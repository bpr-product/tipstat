# MEMORY.md

Design of the memory service in this repo (`backend/source/`). Numbers and limits below are what the code does today.

## 1. What I store, and what I throw away
- **Every message is kept as a raw source** (chat turns, app events) so evidence can be quoted. **Facts** are extracted from it: one model call for a chat message or a free-text app event (Slack text, email, doc, comment); **no model call** for greetings/acknowledgements and for structured app events (calendar, task, reminder, contact), which are applied in code.
- A fact is `subject / relation / value` + kind (`STATE PREFERENCE EVENT PLAN TODO RULE DERIVED`) + **attribution** (`user` or `other`) + an **exact quote** from the source. Code rejects a fact whose quote is not in the source text. Relative dates are resolved against the message timestamp at write time ("now" is the latest message time); an unknown date stays unknown.
- Dropped: small talk, noise, acknowledgements, forget requests (not facts). **Assistant lines are never a source of facts**; they stay inside the raw chat source (for context and keyword/vector matching) but are stripped from the evidence shown to the answer model and to the agent, so the assistant's own words cannot become authoritative.
- The raw message is also kept as a **searchable source** even when no fact was extracted from it; the product UI says which of the two happened.
- A statement that something is **over** ("used to", "until", "no longer", "formerly") is stored as a *former* value, not a current one: the model flags it and code accepts the flag only if the words say so. A to-do or plan that has been completed or cancelled replaces the open one (the model names it; code validates the target).
- **Said vs inferred vs pasted:** only the user's own chat lines or user-sent events can be `user` facts. Text written by others (inbound events) is forced to `other` **in code**; text inside a pasted or forwarded block (From:/Subject:/"wrote:"/quoted lines) is forced to `other` **in code**. A rule or instruction that arrives that way is stored as a fact about that content and is never a standing rule or a command: only `user` rules are enforced. A fact is `sensitive` only if the user asked for privacy or it is a credential; when the same fact is restated with a privacy request the stored fact becomes private (never the reverse). `DERIVED` facts must name stored parent facts or they are dropped.

## 2. How it is stored
SQLite (stdlib, one file, offline). Tables: `sources`, `facts` (status, predecessor, ended time, effective date/time, cardinality, conflict link, sensitive flag), `evidence` (fact to message + quote), `dependencies` (derived fact to parents), `embeddings` (vectors, optional), an FTS5 index over facts and sources, `forget_log` (counts only), `meta`. SQLite because it needs no service, survives restarts and runs inside the fixed container; FTS5 gives BM25 for free. Vectors come from a **local** model (`BAAI/bge-small-en-v1.5` via fastembed/ONNX, baked into the image by `build.sh`, loaded with `local_files_only`); if it is missing the service runs on keyword search alone. The product UI keeps its own storage, one SQLite file per project, separate from the evaluation database.

## 3. What happens at recall time
1. One small model call proposes keywords (skipped when nothing is stored). 2. Search all ages: BM25 over facts and sources, plus cosine over local vectors, merged with **Reciprocal Rank Fusion**; the rest of a matched set, predecessor versions and (for "this week / upcoming / important" questions) due-in-14-days items and open to-dos are added; a two-part question is also searched per part. 3. Items are labelled `CURRENT / EARLIER VERSION (with how many versions before the current value, so "the one before" is unambiguous) / FORMER / no longer valid / CONFLICTS / PAST` (past only for events, plans and to-dos whose date has passed, never for a state that merely has a "since" date), with who said it for others' facts, plus the user's own handle and handles that share a first name. 4. About 3,300 estimated tokens of items go to one answer call (total with the keyword call stays under 4,000). 5. Citations are checked against what was actually supplied; **evidence returned = validated citations only**.
It says "I don't know" when nothing is retrieved (no answer call), when no valid citation supports a claim, or when a current-state answer rests only on outdated versions. A forget/remember *command* sent to `/answer` gets a fixed "Ask only reads" reply instead of a promise.

## 4. How a fact changes
The extraction call sees up to six related stored facts and may name one to `replace`. **Code decides:** the target must be one it was shown, still active, and share words with the new fact; a statement dated earlier than the current fact is stored as history and does not displace it. A replaced fact becomes `superseded` with its end time and the new fact links back to it, so history is kept and "what was it before" works. An exact or paraphrased restatement of an active fact (same value, **same attribution**, similar relation) only adds evidence; the same statement from the user and from someone else stay two facts with their own attribution. An exclusive value with no valid replace is flagged as conflicting, except a temporary exception or a date-specific value ("just for today", "this Friday only", or a dated fact against a standing one), which sits beside the standing value; both stay current and the answer is told to prefer the later one and say it is unsure. Structured events merge by entity id (new state = old state + changed fields). Facts derived from a replaced fact go `stale`. Values come from quotes; nothing is summarised, so consolidation cannot drift from what was said.

## 5. What a delete removes
Only the user's own words can ask (chat, or a user-sent event), never inbound or pasted text. A cheap wording check triggers one model call that may pick stored items **it was shown**; code then closes the set: every version of the fact, facts derived from it (transitively), every raw source that evidences it, copies that contain its quote, and paraphrased copies sharing two or more distinctive words. Independent facts from the same message survive with their own quotes. Rows, search entries, vectors and dependency edges are erased in one transaction, with secure delete, index merge and VACUUM; a check scans for leftovers and a **counts-only receipt** records the result. The request text itself is not kept, and neither is any fact the extraction call made out of the forget sentence (also when nothing stored matched, or when the decision call failed and the sentence is a plain "forget ..."). A broad request ("everything about X") also removes every fact and source that names a capitalised name from the request. Saved product chats and conversation titles that carried the information are redacted, **including when only a raw source (no fact) is erased**: a receipt or answer is redacted when it references an erased fact id (a cited one, for answers), when its visible text contains an erased phrase, a name or long number that is gone from memory, or a word pair containing a gone word; the other half of that turn goes with it; an erased fact that was only an uncited candidate is dropped from an answer's retrieval list instead. Dates, ids and metadata are never compared, so unrelated responses survive. **Limits, stated plainly:** only this app's stores (not the model provider's logs, the harness records or answers already returned); a paraphrase far from the stored wording survives unless the model selected it; matching of the forget sentence to facts is by shared content words, and the in-memory term guard may also block a harmless word pair that only occurred in the erased message; if the decision call fails nothing is deleted and the receipt says so. Later writes by `/act` are blocked from containing forgotten names or word pairs using **salted hashes kept in process memory only** (nothing derived from erased text reaches disk; the guard is lost on restart, deleted data stays deleted).

## 6. The agent
`/act` builds a memory context (the user's standing rules, upcoming commitments the calendar may not show, relevant current facts, outdated versions labelled "do not act on", identity note), then runs a bounded tool loop over the world's HTTP tools (all 29 schemas, at most 12 model calls, 52k estimated tokens, 80 s). **Before every write a backend guard runs; the prompt is not relied on:** quiet-hours rules (matched on recipient, mention, the author of the thread being answered, and the scheduled time), overlap with timed commitments only memory knows, private and forgotten terms, dates that were replaced, recipients never seen in the request/memory/tool results, cancel-for-everyone unless asked, identical repeats, and a cap of 12 changes. A blocked call returns advice (schedule it later, leave it out) and nothing reaches the world. `/act` never writes memory. Weak spot: wrong-recipient resolution beyond names/handles is still model judgment.

## 7. Cost
Per message: 0 calls (structured event, acknowledgement), 1 (chat or free-text event), 2 only when the wording looks like a forget request (hard cap is 2). Per answer: 2 (keywords + answer), 0 when nothing is found or the input is a command. Per job: 1 keyword call + the tool loop. Prompts are clipped so one message stays inside 10,000 input tokens and one answer inside 4,000. Embeddings are local and are not LLM calls. The product UI records model calls, tokens (provider-reported when the response has usage, else estimated) and latency for every turn, without extra calls.

## 9. With another day
Deferred on purpose after the second manual review: a change that takes effect in the future ("from next week ...") still supersedes the current value immediately; the fix needs a pending state that activates on its date and a prompt rule for jobs that span the change, and I could not verify it without an evaluation run. Also first: an extraction completeness pass for multi-clause messages and a retry for a failed extraction; effective-date intervals (start and end) instead of one date; semantic (not only lexical) paraphrase detection when writing; an answer-level check that a current claim is not built on outdated items beyond the citation rule; recipient resolution against contacts for the agent; persisting the forgotten-term guard safely. Known weak: the offline judge's keyword scoring is crude, so scores may mislead; arm64 and a screen reader were not tested; the UI was verified in Edge only; the retrieval floor (0.5 cosine) was tuned on one model.
